# Kaggle LLM Swarm and Self-Tuning Proposal Architecture

Status: implementation draft `0.1`  
Branch: `feature/kaggle-llm-swarm-vnext`

## Purpose

This subsystem expands Universal Node Graph from route search over an admitted graph into a much larger, still inspectable proposal ecosystem. It is designed to help construct, criticize, mutate, simplify, and improve AI/ML solution graphs across many Kaggle competitions while preserving the repository's existing compiler, evaluator, evidence, and holdout boundaries.

The objective is not to ask one model for one complete winning notebook. The objective is to create a bounded experimental system that can repeatedly generate distinct hypotheses, compile admissible candidates, run controlled experiments, retain failures, and learn which proposal mechanisms work for which task families.

```text
Kaggle task and immutable rules
        ↓
Task reframing and interrogation swarms
        ↓
Typed proposal artifacts
        ↓
Compiler and policy gates
        ↓
Graph, subgraph, route, node, package, and parameter candidates
        ↓
Controlled local validation and hidden holdout experiments
        ↓
Immutable receipts and measured effects
        ↓
Question, model, persona, mutation, and route belief updates
        ↓
Next bounded proposal round
```

## Non-negotiable authority boundaries

An LLM may:

- rephrase a task while preserving its oracle;
- ask what should happen next;
- nominate a graph, subgraph, node, route, package, feature, validation scheme, ensemble, or mutation;
- criticize omissions, excess, cost, leakage, fragility, and failure modes;
- judge proposals under a declared rubric;
- propose a test and stopping condition.

An LLM may not:

- make an invalid graph valid;
- add permissions, effects, or hidden dependencies;
- directly alter a frozen plan;
- execute proposed code or packages merely because it suggested them;
- read private holdout labels or a hidden evaluator;
- score its own proposal as accepted evidence;
- promote itself or overwrite prior evidence;
- convert self-reported confidence into compiler or promotion authority.

The existing compiler, runtime isolation, task oracle, evidence ledger, campaign boundary, and human promotion gate remain authoritative.

## Implemented modules

### `solutiongraph.proposal_space`

Provides:

- a lazy Cartesian question space;
- graph, subgraph, node, route, mutation, replacement, package, parameter-space, feature, validation, ensemble, resource, diagnostic, task-reframe, research, and stop proposal kinds;
- explicit context exposure profiles;
- strict per-kind payload contracts;
- strict JSON parsing;
- exact semantic duplicate detection;
- adaptive factor learning over questions and models;
- a protected random exploration fraction.

The default Kaggle space composes these axes:

```text
proposal kind
× intent
× focus
× scale
× response shape
× polarity
× persona role
× persona stance
× theory lens
× language lens
× context exposure
× controlled salt
```

The resulting count is intentionally much larger than a static bank of hundreds of thousands of prompts. Variants are generated by index and traversed through a seeded coprime stride, so a run can sample reproducibly without allocating the full product.

### `solutiongraph.proposal_swarm`

Provides:

- model endpoint manifests;
- adapter-neutral request and response records;
- deterministic recorded adapters for fixtures and replay;
- independent, cross-model, blind/full/hybrid, paired-opposition, focus-sweep, random-neighborhood, panel, and Delphi patterns;
- request, parallelism, failure, and cost limits;
- phase-aware batch execution;
- immutable lane and run receipts;
- proposal deduplication;
- confidence-capped panel aggregation;
- disagreement preservation;
- Pareto selection;
- multi-round campaign state and novelty stopping.

### `solutiongraph.integrations.ollama`

Provides a dependency-free Ollama adapter using the local JSON API:

```text
POST /api/chat
stream = false
format = JSON Schema
options.temperature = endpoint temperature
options.seed = endpoint seed
options.num_predict = endpoint token ceiling
```

The transport is injectable. Unit tests therefore validate exact requests and failure behavior without a running daemon. Model discovery uses `/api/tags`.

### `solutiongraph.kaggle_swarm`

Provides:

- exact competition profiles;
- rules, dataset, and sample-submission digest references;
- target, ID, group, and time-column declarations;
- code-competition and internet/external-data constraints;
- runtime and hardware ceilings;
- local-CV, OOF, hidden-holdout, seed, and leakage policy;
- a scarce submission reservation ledger;
- reward projection that defaults to zero public-leaderboard weight;
- mixed deterministic route/mutation and LLM proposal portfolios;
- reusable Kaggle swarm presets.

## Context visibility matrix

The same question can be asked under intentionally different information conditions.

| Exposure | Included information | Main purpose |
|---|---|---|
| `none` | Question only | Independent prior and unusual starting point |
| `task-only` | Task statement | Blind task decomposition |
| `schema-only` | Task, schema, column profile | Column-focused design |
| `data-profile` | Aggregate profile and schema | Data-quality and representation review |
| `blueprint` | Task, rules, blueprint, constraints | Template specialization |
| `graph-summary` | Summary, not full implementation | Mid-information graph review |
| `graph-full` | Full current graph | Targeted mutation and replacement |
| `evidence-summary` | Graph summary and measured evidence | Evidence-informed next experiment |
| `failures-only` | Failures and hard constraints | Failure-driven repair |
| `champion-only` | Current champion and evidence | Local exploitation |
| `alternatives-only` | Non-champion alternatives | Diversity preservation |
| `research-summary` | Public research summary | Research-informed construction |
| `hybrid` | Selected task, data, graph, evidence, and failures | Balanced informed proposal |
| `full` | Every visible section | Maximum-context review |

Hidden sections are kept in a separate field and are never included even in `full`. This is intended for private holdout identities, sealed evaluator material, and other candidate-unreadable information.

## Question families

The generated space covers questions such as:

### Construction

- What complete graph would solve the task under the current metric and resource limits?
- What is the smallest useful subgraph that can test this mechanism?
- Which first compatible node should fill this obligation?
- Which package could satisfy this capability, and what is the dependency-free fallback?
- What should happen next at the currently feasible frontier?

### Completeness and omission

- What did we miss?
- What information would change the route choice?
- Which columns, interactions, groups, time effects, or leakage paths have not been examined?
- Which validation failure would make the current evidence untrustworthy?
- Which alternative task formulation preserves the oracle but exposes a simpler structure?

### Excess and simplification

- Did we add too many obligations?
- Which node is not earning its cost?
- Which feature family is redundant after conditioning on another?
- What is the smallest deletion that can be safely ablated?
- Is the ensemble masking a validation problem rather than adding diversity?

### Opposition and falsification

- Assume the champion mechanism is wrong. What is the strongest rival?
- What counterexample breaks this graph?
- What negative control should fail if the claimed mechanism is real?
- Which public-leaderboard improvement is most likely to reverse privately?
- Which package, model, or representation has the worst hidden operational risk?

### Analogy and cross-disciplinary transfer

- What would an information theorist compress or preserve?
- What would a control theorist treat as state, observation, action, and feedback?
- What would a compiler engineer inline, specialize, cache, or move behind an interface?
- What would an experimental designer randomize, block, repeat, or hold out?
- What symbolic formula can be combined with learned residuals?
- What unsupervised structure can nominate supervised features?

### Scale and response variations

Questions can be requested as:

- yes/no checks;
- 1–5, 1–10, or 0–100 ratings;
- one next action;
- ranked lists;
- pros and cons;
- exhaustive alternatives;
- counterexamples;
- testable hypotheses;
- minimal patches;
- strict JSON proposals.

These response forms are proposal evidence only. A high rating or self-confidence does not bypass execution and evaluation.

## Proposal lifecycle

```text
QuestionVariant
  → LLMRequest
  → LLMResponse
  → strict JSON parsing
  → ProposalArtifact
  → exact semantic deduplication
  → policy and compiler gates
  → candidate graph/route/node/package materialization
  → deterministic fixtures
  → local CV and holdout experiments
  → immutable run receipts
  → panel and Pareto analysis
  → campaign disposition
  → question-value observation
```

Recommended dispositions:

```text
malformed
duplicate
policy-rejected
compiler-rejected
quarantined
fixture-valid
experiment-eligible
development-rejected
development-retained
holdout-confirmed
promoted
rolled-back
```

## Adaptive question learning

The first implementation learns observational factor values for:

- proposal kind;
- intent;
- focus;
- scale;
- response mode;
- polarity;
- persona role;
- persona stance;
- theory lens;
- language lens;
- context exposure;
- salt;
- model endpoint.

A reward is supplied only after downstream evidence exists. The model uses factor means plus an exploration bonus and preserves a random fraction of questions. This allows the system to learn, for example, that:

- blind validation critics are useful on grouped tabular tasks;
- full-context package proposals are more executable than blind package proposals;
- a particular model is strong at node ABI design but weak at leakage review;
- minimalist prompts produce more accepted mutations late in a campaign;
- information-theory lenses produce useful feature proposals for one task family but not another.

This is observational guidance, not compiler authority and not proof of causal superiority.

## Kaggle evidence firewall

The default reward combines:

```text
compiler validity
+ executability
+ normalized local CV lift
+ normalized private holdout lift
+ robustness
+ novelty
- runtime cost
- monetary cost
- failure rate
```

Public-leaderboard lift has a default weight of zero and a policy ceiling of `0.10`. Submissions must be reserved before use. This reduces the risk that repeated proposal rounds simply optimize noise in the public split.

A serious competition campaign should retain at least these lanes:

```text
fixed simple baseline
history-informed deterministic route
history-blind deterministic route
random admitted route
compiler-gated mutation lane
blind LLM proposal lane
full-context LLM proposal lane
failure-driven repair lane
minimalist deletion lane
ensemble/diversity lane
sealed local holdout confirmation
scarce Kaggle submission confirmation
```

## Ollama model portfolio

The system should use different local models for different work instead of treating all models as interchangeable.

Example endpoint roles:

```python
ModelEndpoint(
    id="model-endpoint.ollama-code",
    adapter_id="adapter.ollama",
    model="your-code-model",
    tags=("role.code", "role.node-implementation"),
)

ModelEndpoint(
    id="model-endpoint.ollama-critic",
    adapter_id="adapter.ollama",
    model="your-reasoning-model",
    temperature=0.1,
    tags=("role.validation", "role.red-team"),
)

ModelEndpoint(
    id="model-endpoint.ollama-diversity",
    adapter_id="adapter.ollama",
    model="your-general-model",
    temperature=0.7,
    tags=("role.blind-proposal", "role.analogy"),
)
```

Model lists, versions, prompt digests, temperatures, seeds, and provider metadata belong in receipts. Results from distinct models should not be called independent evidence when they share the same prompt, context, training lineage, or judge.

## Package proposal gate

A package proposal is incomplete unless it records:

- distribution name;
- import name;
- version constraint;
- source repository;
- license;
- capabilities;
- integration plan;
- deterministic tests;
- dependency-free or existing-node fallback.

Recommended later gates:

- exact release, wheel, and source digests;
- repository and maintainer identity;
- platform and Python compatibility;
- native/system dependencies;
- network, filesystem, GPU, and secret requirements;
- license and competition-rule compatibility;
- isolated installation and import test;
- deterministic fixture;
- failure taxonomy;
- comparison against at least one existing node.

## Near-term implementation roadmap

### Phase 1: current draft

- question-space contracts;
- strict proposals;
- swarms and receipts;
- Ollama adapter;
- Kaggle profiles and reward firewall;
- focused tests.

### Phase 2: compiler materializers

Add explicit adapters from proposal payloads to quarantined authoring artifacts:

```text
GraphProposal → GraphRevision draft
SubgraphProposal → SubgraphCatalog candidate
NodeProposal → NodeSpec draft
RouteProposal → admitted selection request
MutationProposal → typed MutationOperation list
PackageProposal → quarantined package-backed node draft
ParameterSpaceProposal → search-space manifest
```

Each materializer must preserve unknown or invalid fields as rejection evidence rather than guessing executable semantics.

### Phase 3: Ollama campaign runner

- model capability discovery;
- model-role profiles;
- per-model concurrency and memory limits;
- prompt and response artifact storage;
- cancellation and retry policy;
- structured-output repair lane;
- semantic duplicate clustering;
- judge and synthesizer phases;
- question-value updates from downstream receipts.

### Phase 4: Kaggle harness

- competition manifest import;
- train/test/schema digesting;
- task-family fingerprinting;
- baseline graph generation;
- local CV and OOF contracts;
- deterministic route and mutation allocation;
- package quarantine environment;
- experiment result normalization;
- submission reservation and receipt;

### Phase 5: graph vNext runtime

- relational bindings rather than semantic numeric positions;
- readiness-driven activations;

- causally closed frontier checkpoints;
- event-first runtime receipts;
- predicate-driven controllers;
- semantic overlays and selector-based mutations.

## Success criteria

The proposal system is useful only when it improves measured downstream outcomes. Track:

- malformed proposal rate;
- exact and semantic duplicate rate;
- policy- and compiler-admission rate;
- fixture pass rate;
- experiment eligibility rate;
- local-oracle acceptance rate;
- normalized CV and holdout lift;
- public/private reversal rate;
- runtime and cost per accepted proposal;
- proposal diversity;
- question-family value by task fingerprint;
- package nomination survival rate;
- rollback rate;
- number of competitions with a reproducible improvement over the fixed baseline.

Winning a paid competition is an aspirational external outcome, not a claim made by the architecture. The engineering target is a reproducible system that explores more valid hypotheses, learns from failures, protects holdouts, and improves its allocation of questions, models, routes, and mutations across many competitions.
